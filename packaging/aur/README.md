# Wusel AUR packaging

A `PKGBUILD` for Arch Linux (and derivatives — Manjaro, EndeavourOS, Garuda,
CachyOS). A split package: builds `wusel` and `wusel-nautilus` (the native
Nautilus extension) from one tagged release tarball, straight from the user's own machine — `makepkg` has network
access, unlike a COPR/OBS/`mock` chroot, so there is no vendoring step here
the way there is for [the RPM](../rpm).

## Build & test locally

```sh
cd packaging/aur
makepkg -si    # -s: install missing makedepends via pacman; -i: install both results
```

## How it works

`build()` runs `cargo build --release --features fuse -p wusel` and `make -C
integration/nautilus` directly. `package_wusel()` stages the binary, the
systemd user unit, and the app icon by hand; `package_wusel-nautilus()`
installs the Nautilus extension and its emblem icons via `make -C
integration/nautilus install DESTDIR="$pkgdir"`
— the Makefile already knows the right paths (`pkg-config --variable
extensiondir`), so there is no reason to hardcode them a second time here.
The cloud-provider (Nautilus sidebar) registration for the default account is
generated by running the freshly built binary during `package_wusel()`, same trick
as the RPM spec, for the same reason: it can never drift from the code that
also writes it at runtime for named accounts.

`wusel` depends on `fuse3` only; `wusel-nautilus` and `gnome-shell` are
`optdepends` — same reasoning as the RPM's `Suggests` over `Recommends`,
see [`../rpm/wusel.spec`](../rpm/wusel.spec). `wusel-nautilus` depends on
`wusel`, `libnautilus-extension` and `glib2` — not GTK, which the extension
is compiled against but does not link. `nautilus` and `gtk4` are
`makedepends`, since building the extension needs their headers.

Verified by building and installing the resulting package into a clean Arch
container: `pacman -Ql wusel` and `pacman -Ql wusel-nautilus` match the
intended file lists exactly, and
`wusel --version` runs. Building via `make ... install DESTDIR=...` surfaced
a real bug the RPM path never hit (it installs the `.so`/emblems by hand, so
it never went through that Makefile target with `DESTDIR` set): the icon
cache refresh in `integration/nautilus/Makefile`'s `install` target got baked
into the staged tree and collided with the file `hicolor-icon-theme` already
owns — see that Makefile's `ifeq ($(DESTDIR),)` guard.

## Publishing

Not done by this repository — an AUR account is a **personal identity**,
like Fedora's FAS for COPR (see the packaging plan's own note on this).
There is no company account to create; whoever registers one should record
here which address it is under and how to regain access, so a package
channel is never orphaned. Once someone has one:

```sh
git clone ssh://aur@aur.archlinux.org/wusel.git aur-wusel
cp packaging/aur/PKGBUILD packaging/aur/.SRCINFO aur-wusel/
cd aur-wusel && git add PKGBUILD .SRCINFO && git commit -m "..." && git push
```

`.SRCINFO` is checked in here too, but **regenerate it on every `PKGBUILD`
change** (`makepkg --printsrcinfo > .SRCINFO`) — AUR's own tooling is what
reads `.SRCINFO`, not `PKGBUILD` directly, and a stale one is a common,
easy-to-miss AUR packaging mistake.

## Bumping the version

Update `pkgver`/`pkgrel` and `sha256sums` (the tag must exist on the public
GitHub mirror first — the `source` URL points at
`github.com/itbh-at/wusel/archive/refs/tags/vX.Y.Z.tar.gz`), then regenerate
`.SRCINFO`.
